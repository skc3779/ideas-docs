# EdgeArrow-Map: 서비스 사이 "화살표"의 숨은 장애 요인을 찾아 주는 엣지 진단 DevTools

## 1. 제안 범위 및 카테고리
- **영역**: 소프트웨어 (Software)
- **세부 카테고리**: DevTools (관측성·신뢰성)
- **직전 실행과의 관계**: 신규

## 2. 해결 문제와 사용자 페르소나
- **문제 정의**: 시스템 아키텍처 다이어그램에서 사람들은 코드, DB, CPU 사용량이 담긴 박스에 주목한다. 그러나 박스 사이의 화살표에도 중요한 작업과 자원, 여러 가정이 숨어 있다. 두 서비스가 모두 정상인데도 한쪽이 커넥션을 기다리거나 오래된 주소로 요청을 보내면 실패가 난다. 기존 모니터링은 서비스 단위 지표가 중심이어서 이런 "사이의 실패"를 원인으로 짚어 주지 못한다.
- **타겟 사용자**: 마이크로서비스 20개 이상을 운영하는 스타트업·중견기업의 SRE, 플랫폼 엔지니어, 장애 대응 당번 개발자
- **페르소나**: 핀테크 스타트업의 플랫폼 엔지니어. 새벽 장애 알림을 받고 대시보드를 보면 모든 서비스가 초록색인데 결제 요청은 간헐적으로 실패한다. 원인은 몇 시간 뒤에야 커넥션 풀 고갈과 DNS 캐시 TTL 불일치로 밝혀진다.

## 3. 핵심 기능 및 차별점
| 기능 | 설명 | 기존 대안 대비 차별점 |
|---|---|---|
| 엣지 건강 지도 | 트레이스로 서비스 간 호출 그래프를 만들고, 엣지별 대기 시간·실패율·재시도 비율을 색으로 표시 | APM 서비스 맵은 노드 지표 중심이고 엣지 설정 정보가 없음 (추정) |
| 설정 불일치 검사 | 호출 측 타임아웃·재시도와 피호출 측 처리 시간·커넥션 풀 크기를 비교해 모순을 경고 (예: 호출 측 타임아웃이 하위 서비스 타임아웃보다 짧음) | 설정 파일과 런타임 데이터를 함께 보는 정적+동적 분석 |
| 오래된 주소 탐지 | 서비스 디스커버리·DNS TTL과 실제 엔드포인트 변경 이력을 대조 | 배포 직후 간헐 실패의 원인을 자동으로 후보에 올림 |
| 장애 리플레이 | 장애 시간대의 엣지 상태를 타임라인으로 재생하고 포스트모템 초안 생성 | 사후 분석에 드는 수작업 감소 |

## 4. 실행 계획 (MVP → 확장)
- **MVP 범위 (0~3개월)**: OpenTelemetry Collector 수신, Kubernetes 매니페스트·Envoy/Istio 설정 파서, 엣지 지도 웹 UI, 설정 불일치 규칙 20개. 만들지 않을 것: 자체 에이전트 SDK, 로그 저장소, 알림 시스템 전체
- **확장 1단계 (3~6개월)**: 커넥션 풀·DNS 지표 수집기, Slack 장애 리포트, GitHub PR 단계의 설정 변경 검사
- **확장 2단계 (6~12개월)**: 카오스 실험 추천(엣지 단위 장애 주입 시나리오), 멀티 클러스터 지원
- **기술 스택**: Go(수집기), OpenTelemetry, ClickHouse, Rego/OPA 기반 규칙 엔진, React + 그래프 시각화

## 5. 수익 모델
- 오픈소스 CLI(설정 검사)는 무료, 호스팅 대시보드는 서비스 수 기준 월 과금(가설: 서비스당 월 과금, 추정)
- 첫 유료 고객 확보 경로: 무료 CLI를 쓰는 팀 중 서비스 수가 많은 조직에 호스팅 버전 체험판 제공

## 6. Go-To-Market
- "다이어그램의 화살표가 실패하는 10가지 방식" 같은 기술 블로그와 오픈소스 CLI를 함께 공개해 ByteByteGo 독자층 같은 백엔드 엔지니어에게 확산
- CNCF 밋업, SRE 커뮤니티의 포스트모템 사례 발표에서 데모

## 9. 실현 가능성 점수: **3 / 5**
- **기술 난이도**: 중간. OpenTelemetry와 설정 파서는 성숙한 기술이지만, 불일치 규칙의 정확도를 높이려면 실제 장애 사례가 필요하다.
- **초기 비용**: 낮음. 1~2명이 3개월 안에 CLI와 기본 UI를 만들 수 있다.
- **시장 진입**: 보통. 관측성 시장은 경쟁이 치열하므로 설정 검사라는 틈새가 유료로 이어질지 검증해야 한다.
- **수요 신호**: 1건. 서비스 간 숨은 실패를 다룬 ByteByteGo 글 하나뿐이라 규칙상 3점으로 매겼다. 백엔드 엔지니어 대상 매체에서 다룰 만큼 관심 있는 주제라는 점은 참고가 된다.
